# Uploading your own images — no code, no redeploy

**Status: live.** The site's leadership photos serve from your Cloudinary
account (cloud name `mov8hypa`) as of 2026-09-21. The 5 existing photos were
seeded in already, so nothing changed visually at cutover — replace one
whenever you're ready, following the steps below.

Setup note for the record: activating this only ever needed the Cloud name
— no API key or secret is stored in this repo, in Railway's config, or
anywhere else; the site only *reads* public image URLs. An API key/secret
was shared once during setup to seed the initial 5 photos programmatically
(saving a manual re-upload); it was used from an env var on a single local
command, never written to a file, and the script was deleted immediately
after. If you're reading this because you're rotating that Cloudinary API
key as routine hygiene, it's safe to do any time — nothing on the site
depends on it.

## Uploading or replacing a photo

1. Open the **Media Library** in the Cloudinary dashboard.
2. Create the folder structure once: `bluewhalestack/team/`.
3. Drag in a photo. When you name it (or set its Public ID), use **exactly**
   the person's slug from the filenames already in `public/team/` — e.g. a
   new photo for the founder is uploaded as
   `bluewhalestack/team/abhishek-pangerkar` (no file extension in the box
   Cloudinary gives you for the Public ID; it detects the format itself).
   Replacing an existing photo: upload with the **same** Public ID and tick
   **"Overwrite"** — the live site updates on next page load, nothing to
   redeploy.
4. New person joining, no photo yet in the repo: add them to
   `content/about.ts` first (ask Claude, or add the `leadership` entry
   yourself) — the photo slot only appears once that entry exists.

## The convention, if we add more image slots later

Today only the leadership/team photos go through this system (they're the
one place on the site with a hand-maintained real photograph — most other
imagery is generated by the design system: 3D product renders, diagrams,
icons). Any future slot follows the same three-line pattern:

```ts
import { cld, publicIdFromPath } from "@/lib/cloudinary";
// local path already in /public, e.g. "/customers/acme-hq.jpg"
const src = cld(publicIdFromPath(localPath, "customers"), localPath, 800);
```

`cld()` returns the Cloudinary URL once `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`
is set, and the original local file untouched if it isn't — so wiring a new
slot in is never a breaking change, and there's always a fallback checked
into the repo even if Cloudinary is ever unreachable.

See `lib/cloudinary.ts` for the implementation.
